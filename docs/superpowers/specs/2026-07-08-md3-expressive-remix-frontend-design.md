# JM Aura Remix 前端 MD3 Expressive 重构设计

## 背景

当前前端已经具备基础的 Remix 页面、MD3 token、搜索页、详情页、阅读器雏形，以及与 Hono 后端的核心对接能力，但整体仍然停留在“功能页面集合”的状态，缺少统一的信息架构、持续一致的视觉语言，以及围绕“漫画阅读”这一核心场景进行的产品化组织。

与此同时，后端能力已经明显增强：

- 首页聚合：`GET /api/home`
- 搜索：`POST /api/search`
- 分类与子分类：`POST /api/categories`
- 排行：`GET /api/rankings/today|week|month`
- 登录：`POST /api/auth/login`
- 收藏夹：`GET /api/favorites`、`POST /api/favorites`
- 导出与任务：`/api/tasks/*`
- manifest 与图片代理：`GET /api/export/album/:id/manifest`、`GET /api/image/proxy`

因此，这次前端重构的目标不是“换皮”，而是将前端真正升级为一套围绕阅读体验构建、能够完整承接后端能力的漫画应用。

## 目标

### 产品目标

将前端重构为一个以“继续阅读优先”为核心的一体化漫画应用，使用户打开应用后可以：

1. 第一时间回到上次阅读位置
2. 在搜索、分类、排行之间高效切换
3. 在详情页快速判断并进入下一步阅读
4. 在阅读器中长时间阅读而不感到视觉疲劳
5. 在“我的”页完成登录、收藏、任务查看与导出下载

### 设计目标

构建一套完整的 **MD3 Expressive** 前端视觉系统，具备：

- 深浅双主题
- 明确的层级容器语言
- 极致舒适的排版与配色
- 丝滑但克制的动效
- 在中文阅读场景下稳定、耐看的长时间使用体验

### 工程目标

- 完全适配现有 Hono 后端接口
- 保持高性能与高易用性
- 以体验优先为前提，尽可能压低前端运行时占用、重绘成本与长期驻留内存压力
- 明确适配 Safari（尤其是 iOS Safari）与全尺寸屏幕，不将交互建立在单一 Chromium 行为上
- 在不引入不必要复杂度的前提下完成全站重构
- 保持页面职责、组件职责、数据职责清晰分离

## 设计总方向

本次重构采用 **“阅读中枢型 MD3 Expressive 漫画应用”** 的方向，而非传统内容平台首页。

### 总体原则

- **继续阅读优先**：首页第一视觉焦点必须是“继续阅读”
- **双主题同气质**：深色沉浸、浅色纸感，但信息结构不变
- **Expressive 但不吵**：强调 shape、层级、动线、滚动节奏，不做高噪音装饰
- **后端能力前置适配**：页面结构围绕现有 API 能力组织，而不是前端自造假状态

## 信息架构

整站分为 6 个主区域：

| 区域 | 角色 | 核心接口 |
| --- | --- | --- |
| 首页 | 阅读中枢，继续阅读优先 | `GET /api/home` |
| 搜索 | 高效检索与筛选 | `POST /api/search` |
| 发现 | 分类、子分类、排行、过滤 | `POST /api/categories`、`GET /api/rankings/*` |
| 详情 | 阅读决策页 | `GET /api/manga/:id`、`POST /api/favorites` |
| 阅读器 | 沉浸式阅读空间 | `GET /api/chapter/:id`、`GET /api/image/proxy` |
| 我的 | 账户与能力工作台 | `POST /api/auth/login`、`GET /api/favorites`、`/api/tasks/*` |

主导航建议固定为：

- 首页
- 搜索
- 发现
- 我的

阅读器不进入主导航语义，而作为独立沉浸上下文存在。

## 页面级设计

### 首页

首页将被重构为 **阅读中枢页**。

#### 第一屏结构

第一屏由 3 个层级构成：

1. **继续阅读主卡**
   - 当前最大视觉焦点
   - 展示最近阅读作品、上次章节、阅读进度、继续按钮
   - 允许一键回到最近章节
2. **快速检索带**
   - 更轻量的搜索入口
   - 始终可达，但不抢首页主焦点
3. **今日发现副栏**
   - 基于 `GET /api/home`
   - 展示 `latest` 和 `rankings.today` 的轻量横向内容带

#### 后续区块

首页下方按以下顺序组织：

- 继续阅读历史
- 最新更新
- 今日 / 本周 / 本月排行切换块
- 收藏与导出任务概览

#### 首页交互原则

- 顶部 app bar 随滚动压缩
- 排行切换采用局部内容刷新与过渡，不做整页切换
- 继续阅读卡在移动端与桌面端都保持一键进入阅读器
- 首页不做重型瀑布流，优先可读性与首屏速度

### 搜索页

搜索页被定义为 **检索工作台**。

#### 结构

- 搜索输入与当前上下文
- 筛选面板：`main_tag / order_by / time`
- 结果区：高密度但不拥挤的封面网格

#### 交互原则

- URL 参数始终保真，支持分享与回退
- 翻页必须保留筛选条件
- 搜索中优先保留旧结果与上下文，减少闪烁
- 唯一命中场景需要明显突出“直达详情”

### 发现页

发现页将成为真正的 **categories_filter 页面语义** 承载者。

#### 数据来源

- 默认分类流：`POST /api/categories`
- 快捷排行：`GET /api/rankings/today|week|month`
- 子分类：`sub_category`

#### 页面结构

- 大颗粒分类轨道
- 子分类与过滤轨道
- 内容流网格

#### 原则

发现页不能等同于搜索页。搜索页是“明确意图检索”，发现页是“浏览型探索”。

### 详情页

详情页定义为 **阅读决策页**。

#### 结构

- 大封面头部
- 动作区：继续阅读 / 从第一话开始 / 收藏 / 导出
- 简介与元信息区
- 章节列表
- 相关作品区

#### 原则

- 用户进入详情页后，应当快速完成“判断作品 + 决定下一步”
- 收藏与导出入口必须是真实功能入口，而不是装饰按钮
- 对长章节列表提供清晰的当前阅读位置指示

### 阅读器

阅读器是本次重构的体验重心。

#### 目标

实现一个真正适合长时间阅读的沉浸式空间。

#### 结构

- 图片阅读流
- 顶部浮层导航
- 底部操作区
- 阅读偏好面板

#### 原则

- UI 默认低干扰，交互时再出现
- 不使用会打断阅读节奏的高噪音动画
- 图片显示稳定、加载顺、切换章自然
- 深色主题优先为阅读器做优化

### 我的页

“我的”页是账户与工具能力工作台，而不是空壳个人页。

#### 结构

- 登录状态卡
- 收藏夹与文件夹切换
- 导出任务与下载区
- CLI / Web 协同提示

#### 原则

- 承接 `favorites` 与 `tasks`
- 清楚区分“正在执行”“可下载”“已过期”
- 提供明确的下一步动作，而不是只展示状态

## 视觉系统

### 设计气质

本次视觉方向采用 **柔和雕塑感 + 编辑排版感** 的 MD3 Expressive。

不是强调“潮流 UI”，而是强调：

- 可长时间使用的舒适度
- 内容与功能的层级明确
- 具有辨识度但不喧闹的界面气质

### 双主题策略

#### 深色主题

关键词：

- 沉浸
- 夜读
- 包裹感
- 更深的层级与对比

适用场景：

- 首页继续阅读主卡
- 详情页头部
- 阅读器
- 我的页任务区

#### 浅色主题

关键词：

- 纸感
- 编辑感
- 透气
- 更轻的阅读负担

适用场景：

- 搜索
- 发现
- 长列表浏览
- 白天阅读

### 色彩系统

建立 4 层色彩语义：

1. 背景层
2. 容器层
3. 强调层
4. 阅读保护层

其中阅读保护层用于限制阅读器与长时间浏览页面中的高刺激色使用。

### Shape Language

形状作为层级表达的一部分：

- 主容器：大圆角、较强包裹感
- 次级容器：更克制的曲率
- 功能控件：强调可点击与状态反馈
- 浮层 / 面板：具有“被托起”的感觉

### 排版策略

- 标题需要辨识度，但不能破坏中文正文可读性
- 正文、元信息、章节、标签要有严格字级差
- 首页与详情偏编辑排版
- 阅读器偏功能排版
- 控制单列内容宽度，避免视觉发散

## 响应式与兼容性策略

适配性不是附加项，而是本次重构的设计前提。

### 浏览器兼容

重点覆盖：

- Safari macOS
- iOS Safari
- Chromium 系浏览器

实现上必须满足以下要求：

- `backdrop-filter` 必须有可接受的无模糊降级样式，不能依赖模糊才能成立
- 视口高度必须考虑 iOS Safari 地址栏伸缩，避免页面跳动与底栏抖动
- 顶部浮层、底部导航、阅读器底栏都要与 `safe-area-inset-*` 一起设计
- 不能依赖仅在新版本 Chromium 中才稳定的 CSS/JS 特性作为核心交互基础
- 触摸滚动、横向滑动和惯性滚动以移动 Safari 为基准验证

### 全尺寸屏幕适配

需要覆盖：

- 小屏手机
- 大屏手机
- 平板竖屏 / 横屏
- 常规桌面
- 超宽屏与大尺寸桌面屏

适配原则：

- 首页和发现页在大屏上要升级为多区块编排，而不是简单拉宽
- 搜索页与我的页允许在桌面端进入双栏 / 多栏布局
- 阅读器和详情正文必须有受控最大宽度，避免超宽屏阅读疲劳
- 关键操作区在任意尺寸下都保持稳定可达，不因布局切换而消失

### 安全区与系统 UI

- 必须适配 `env(safe-area-inset-top/right/bottom/left)`
- 底部导航、阅读器底栏、抽屉面板和浮动操作区都要避免被 Home Indicator 遮挡
- 横屏和异形屏下，核心按钮与进度信息仍需保持可点击和可见

## 动效策略

动效目标不是“炫”，而是让用户感到顺。

### 应重点实现的动效

- 首屏模块 stagger 入场
- 顶部 app bar 滚动压缩
- 卡片 hover / active / focus 状态反馈
- 主题切换过渡
- 搜索与过滤切换时的局部过渡
- 阅读器控件出现 / 消失

### 应避免的动效

- 过度位移
- 大幅弹性
- 长时遮挡内容的转场
- 对阅读形成干扰的装饰动画

## 性能与可用性

### 数据层原则

- 首页优先聚合接口 `GET /api/home`
- 发现页使用 `POST /api/categories`
- 搜索页维持 URL 驱动
- 每个页面 loader 只请求自己真正需要的数据
- 减少页面级并发拼装请求，优先使用聚合或直达接口，降低首屏抖动与状态复杂度

### 渲染层原则

- 图片组件统一使用渐进加载策略
- 阅读器减少不必要 DOM 包裹
- 保持组件边界清晰，避免全局 re-render
- 长列表与阅读器优先控制同屏节点数量，避免驻留时间增长后占用持续膨胀
- 优先稳定布局，减少图片加载引起的大幅 reflow
- 封面网格、章节列表、任务列表等区域坚持轻 DOM 与浅层结构

### 样式层原则

- 以 CSS 变量驱动主题系统
- 动效优先 CSS 原生
- 不引入不必要的重型前端状态系统
- 高成本视觉效果必须可降级，不能依赖持续滤镜、重阴影或大面积实时动画
- 优先使用 `transform` / `opacity` 参与动画，减少 layout 与 paint 压力

### 交互层原则

- 切换状态时尽量保留上下文
- 分页、筛选、局部刷新优先
- 减少整页闪烁与重排
- 触屏与鼠标两套交互都必须顺滑，hover 不能成为唯一反馈方式
- 所有关键交互必须在 Safari 下稳定成立，不能出现“能看但不好点”的情况

### 性能与占用优先级

本次重构遵循以下优先级：

1. 阅读与操作的稳定性
2. 首屏速度与滚动顺滑度
3. 内存 / 占用控制
4. 视觉表现

这意味着：

- 若高成本视觉效果会显著影响滚动、掉帧、耗电或 Safari 稳定性，则必须降级或移除
- 阅读器优先保证连续阅读稳定，不为视觉包装增加额外占用
- 首页、搜索、发现页的过渡效果必须服务于顺滑，而不是制造展示型负担

## 与后端接口的适配策略

### 首页

- 首选 `GET /api/home`
- 首页只消费聚合数据，不自行并发拼接多个 ranking/category 请求

### 发现

- 使用 `POST /api/categories`
- 完整承接：
  - `category`
  - `sub_category`
  - `order_by`
  - `time`

### 搜索

- 使用 `POST /api/search`
- URL 参数与 loader 数据一一对应

### 我的

- 收藏：`GET /api/favorites`
- 添加收藏：`POST /api/favorites`
- 任务：`GET /api/tasks`、`GET /api/tasks/:id`、`GET /api/tasks/:id/download`

### 导出相关体验

- Web 前端不伪造下载状态
- 任务进度、可下载状态、过期状态与后端保持一致
- 对 CLI 更适合的重型操作要做轻提示，不强行在 Web 中模拟 CLI 工作流

## 实现边界

### 第一阶段

先完成结构与核心体验重构：

- 全局 shell
- 导航系统
- 双主题
- 首页
- 搜索页
- 发现页
- 详情页
- 阅读器
- 我的页

### 第二阶段

再接深增强能力：

- 收藏夹文件夹切换
- 导出任务实时体验增强
- 阅读偏好持久化
- 更多错误态与空态

## 文件与模块改造策略

前端将按以下层次组织：

- 布局层
- 设计系统层
- 页面层
- 数据适配层
- 体验层

原则：

- Route 文件负责页面编排
- 组件负责表达
- 数据适配文件负责接口映射
- 避免 route 与组件继续膨胀成大文件

## 风险控制

### 风险 1：重构范围过大

缓解方式：分两阶段实施，先保证整体体验与核心阅读链路成立。

### 风险 2：视觉优先压过可用性

缓解方式：阅读器与详情页始终以“舒适”和“清晰”为第一优先级。

### 风险 3：Expressive 导致性能下滑

缓解方式：动效优先 CSS，数据优先聚合，减少前端不必要运行时复杂度；所有高成本视觉效果都必须具备降级方案。

### 风险 4：与后端能力脱节

缓解方式：所有主要页面设计均围绕现有 Hono API 组织。

### 风险 5：Safari / 全尺寸屏幕下体验断裂

缓解方式：从布局、动效、导航、安全区、视口高度策略开始就按 Safari 与多尺寸屏幕设计，不把适配留到最后修补。

## 建议实现顺序

1. 全局 shell、双主题、导航、首页
2. 搜索页与发现页
3. 详情页与阅读器
4. 我的页、任务、收藏与细节状态

## 最终结论

本次前端重构的目标，是将项目升级为：

**一个以继续阅读为第一优先级、以双主题 MD3 Expressive 为视觉骨架、以 Remix + Hono 接口严密贴合为工程基础的高性能漫画阅读应用。**
