# JM Aura Remix 移动站点化与桌面网站化 UI 重设计

## 背景

当前 Remix 前端在功能上已经具备首页、搜索、发现、详情、阅读器、我的页，以及基于 `defer` 的分段流式加载、顶部细进度条和局部错误重试能力，但界面仍存在明显的结构问题：

- 手机端存在重复块、遮挡、偏移和间距不稳定
- 多个页面仍保留明显的 App 壳层感，与漫画站点浏览习惯不一致
- 电脑端虽然可用，但本质上更像“放大的手机 UI”，不够像真正的大屏网站
- 整体卡片、标题、模块容器过大，导致同屏信息密度偏低

用户已经明确新的方向：

1. 全站做一次系统性的 UI/UX 收敛
2. 手机端改为更像 `jm-aura` 的漫画站浏览体验
3. 手机端内容流以双列 / 3 列为主，而不是大卡单列
4. 电脑端不再复用移动端放大布局，而是单独设计更适合桌面网站的 UI
5. 风格参考 `jm-aura`，但不做 1:1 复刻
6. 保持 Remix 的高性能、高兼容和当前流式加载体系

## 目标

### 产品目标

将现有前端从“结构完整但形态偏 App 化”的界面，重构为一套更接近真实漫画站点的浏览型前端：

- 手机端更像漫画站，而不是内容卡片 App
- 桌面端更像电脑网站，而不是手机页面拉宽版
- 内容浏览效率明显提高
- 同屏展示数量提高，但不牺牲可读性和点击可用性

### 体验目标

- 消除重复、遮挡、错位和尺寸失衡
- 手机端首屏优先展示漫画内容而不是说明性块
- 手机端默认采用双列 / 3 列内容流
- 桌面端拥有独立的信息架构和布局节奏
- 全站更接近 `jm-aura` 的漫画站浏览体验

### 工程目标

- 不改变现有 Remix 路由结构与 Hono API 契约
- 保留现有 `defer + Suspense + Await` 流式数据链路
- 保留局部错误、局部 loading、局部 retry 机制
- 优先通过组件收敛、断点重组和 CSS 重构完成改造
- 不引入重型前端运行时依赖，不牺牲 Safari 和移动端兼容性

## 设计方向

本轮采用以下总方向：

**移动端站点化，桌面端网站化的双轨 UI 重设计。**

其含义是：

- 移动端不再强调强 App 壳感，而是更接近漫画站内容浏览
- 桌面端不再只是响应式拉宽，而是单独设计成更适合大屏的网站 UI
- 两端共用同一套业务逻辑、数据结构和加载模型
- 通过断点切换布局与组件变体，而不是复制两套前端

## 范围

本轮覆盖以下页面与全局壳层：

- 首页
- 搜索页
- 发现页
- 详情页
- 阅读器
- 顶栏 / 底栏 / 全局导航壳层

本轮不作为主要修改对象的内容：

- 后端接口协议
- 业务 loader 数据来源
- 任务、导出、登录等后端功能逻辑
- 主题系统的基础 token 架构

## 总体原则

### 内容优先

页面首先服务于浏览、检索和阅读，不再让说明性文案和大块装饰容器占据主视线。

### 双端分轨

移动端与桌面端采用不同的信息架构和布局节奏，但共用数据层与交互语义。

### 漫画站优先

整体参考 `jm-aura` 的站点型内容组织方式，强调封面流、频道感和浏览效率，而不是 App 式任务卡片堆叠。

### 轻运行时

优先通过 CSS、结构重组和有限状态控制解决问题，避免引入高频计算和复杂客户端布局逻辑。

### 局部容错不回退

UI 改造不能破坏现有的流式加载、局部 loading、错误隔离和独立重试。

## 移动端策略

### 总体方向

移动端采用“更像漫画站”的内容首页与内容流布局，弱化当前过重的 App 壳感。

### 壳层调整

- 保留顶栏，但减少过厚容器感和过多背景存在感
- 保留底部导航，但下调视觉权重，避免持续压制内容区
- 统一 `safe-area`、顶栏占位、底栏占位和滚动容器边界
- 优先解决 fixed 顶底栏导致的遮挡、偏移和重复感

### 内容流规则

移动端默认采用：

- `双列` 作为基础内容流布局
- 更宽手机进入 `3 列`
- 不再默认使用大卡单列

适用区域包括：

- 首页内容流
- 搜索结果
- 发现页结果网格
- 相关推荐
- 详情页中的辅助内容区

### 卡片规则

移动端卡片采用“封面主导、文字收紧”的漫画站样式：

- 封面占比更高
- 标题保留 1 到 2 行
- 元信息缩减为最必要内容
- 减少独立说明区、标签堆叠和多层内边距
- 视觉上“更大一点”，但空间更多分配给封面和同屏网格，而不是胖容器

### 文案规则

移动端各页减少以下内容：

- 教程式说明
- 英雄区宣传语
- 冗长区块描述
- 与核心任务无关的解释性文案

保留的文案只服务于：

- 状态
- 错误
- 空态
- 操作结果

## 桌面端策略

### 总体方向

桌面端单独设计为更适合电脑网站的信息架构，整体体验参考 `jm-aura`，但不机械复刻。

### 布局原则

- 桌面端不复用移动端底部导航语义
- 桌面端不保留“放大的手机卡片页”观感
- 页面结构以横向信息组织、频道布局和更高密度网格为核心
- 鼠标操作、Hover、宽屏浏览路径需要成为主要设计依据

### 首页

桌面首页改为更像网站的内容首页：

- 首屏直接进入内容，不再放置大块 App 式 hero 容器
- 通过横向内容带、频道区块和高密度网格组织首页
- 搜索入口、分类入口和继续阅读都作为辅助结构出现
- 继续阅读不再霸占首页第一视觉焦点

### 搜索与发现

桌面搜索与发现改为更适合大屏的网站工具区：

- 筛选条件更适合放在顶部工具带或上方区域，而不是沿用移动抽屉视觉
- 结果网格显著提密
- 状态提示轻量化，避免大块状态面板压缩主结果区
- 分类导航与结果区形成清晰频道关系

### 详情页

桌面详情页采用更标准的分栏阅读决策布局：

- 左侧放封面与核心信息
- 右侧作为章节、评论和主内容区
- 主操作与元信息紧邻封面主体
- 章节与评论切换不再挤压头部信息区域

### 阅读器

桌面阅读器采用单独的大屏阅读策略：

- 单独控制阅读宽度，不沿用移动端拉宽逻辑
- 提供更合理的章节切换与进度辅助
- 保持阅读沉浸，但允许更适合鼠标的大屏操作布局

## 页面级设计

### 首页

### 移动端

首页改为直接进入内容流，默认顺序为：

- 搜索入口
- 最新更新
- 热门内容
- 分类快速入口
- 缩小后的继续阅读

首页删减内容：

- 过重 hero 区
- 模块宣传语
- 解释性大文案
- 与浏览无关的装饰块

### 桌面端

首页改为网站式内容首页：

- 上部为搜索 / 快捷频道 / 热门切换
- 中部为高密度内容区块
- 下部或侧边承载继续阅读与辅助模块
- 强调同屏可见作品数量

### 搜索页

### 移动端

- 搜索框直接可用
- 高级筛选默认收起，避免首屏拥挤
- 结果区采用双列 / 3 列内容流
- 唯一命中、空结果、错误结果采用轻量局部状态

### 桌面端

- 顶部横向工具条承载搜索与筛选
- 结果网格高密度展示
- 当前筛选上下文清晰可见
- 分页与排序不再与结果主区发生视觉冲突

### 发现页

### 移动端

- 分类切换和次级筛选分层组织
- 避免分类、子分类、排行、筛选全部堆在首屏
- 结果区保持双列 / 3 列浏览节奏

### 桌面端

- 顶部为分类导航与筛选带
- 中部为频道式结果区
- 页面整体更像站点频道，不像移动抽屉摊平版

### 详情页

### 移动端

- 压缩当前过大的 hero 容器
- 移除负边距和过强背景装饰带来的错位感
- 信息、操作、章节、评论重新分层
- 推荐区和辅助内容区优先双列小卡

### 桌面端

- 改为两栏或 1.5 栏结构
- 左侧固定封面与主信息
- 右侧承载章节、评论和操作区
- 视觉重心从“大封面背景块”转为“清晰阅读决策结构”

### 阅读器

### 移动端

- 保持原生 Webtoon 连续阅读
- 修复顶部和底部控件对图片流的遮挡
- 统一 `safe-area`、控件显隐和滚动时机
- 减少与阅读内容竞争注意力的装饰性元素

### 桌面端

- 采用独立的阅读宽度策略
- 控件以辅助方式出现，不持续打断图片流
- 保持沉浸感的同时提供更合理的大屏可操作性

### 顶栏与底栏

### 移动端

- 统一顶栏高度
- 统一底栏占位高度
- 统一进度条与 fixed 层级关系
- 避免顶栏、搜索入口、局部面板之间产生重复容器感

### 桌面端

- 以顶部网站导航替代移动端底部导航语义
- 页面内工具区与全局导航职责分离
- 减少桌面端对移动导航模式的依赖

## 组件策略

本轮优先收敛一套可复用基础组件，而不是在页面中继续堆叠大型容器。

### 基础组件

- `PageHeader / SectionHeader`
- `MediaCard` 多尺寸变体
- `Toolbar / FilterBar / FilterDrawer`
- `DetailHero / ChapterList / CommentPanel`
- `ReaderOverlay`

### 收敛规则

- 相同语义页面头部统一结构
- 卡片只保留有限尺寸档位
- 筛选语义统一，但移动端与桌面端呈现不同
- 详情页与阅读器的复杂控件从页面本体中拆离，降低错位风险

## 断点策略

断点采用明确的职责切分，而不是单一布局线性拉伸。

### 手机

- 内容优先
- 双列 / 3 列内容流
- 保留移动导航，但弱化壳感

### 平板 / 小桌面过渡

- 只做必要结构过渡
- 避免同时混入完整桌面和完整移动语义

### 桌面

- 启用独立的网站式布局
- 启用更适合鼠标的大屏筛选与分栏结构
- 底部导航退出主要导航语义

## 加载、容错与状态规则

### 保留的能力

- 顶部细进度条
- 首页与其他页面的分段流式骨架屏
- 各区块独立错误态
- 各区块独立重试

### 强制要求

- UI 改造不能把流式区块重新耦合为整页阻塞
- 评论、收藏探测、次级信息继续保持按需加载
- 错误态必须轻量，不得以大面积面板破坏内容节奏
- loading skeleton 必须与新的双列 / 3 列网格对齐

## 性能与兼容边界

### 性能边界

- 不引入重型布局计算库
- 不增加高频 `resize` 测量和大规模客户端状态同步
- 尽量复用现有组件与数据获取模型
- 优先使用 CSS Grid、Flex 和已有布局工具完成改造

### 兼容边界

- 保持 Safari、iOS Safari 和 Android Chrome 可用
- 明确处理 `100vh / 100dvh / safe-area` 差异
- 固定定位元素必须在移动端真实验证遮挡关系
- 阅读器长章节渲染不引入明显额外开销

## 测试重点

本轮测试重点如下：

- 手机端首页、搜索、发现、详情、阅读器是否仍有遮挡或偏移
- 手机端双列 / 3 列网格在不同宽度是否稳定
- 桌面端是否已经摆脱“放大的手机 UI”
- 顶栏、底栏、进度条、流式骨架与局部重试是否仍正常
- 详情页章节与评论切换是否不再引发布局挤压
- 阅读器图片流与控件显隐是否稳定

## 实施顺序

实现按以下顺序推进：

1. 先重构全局壳层、断点和基础布局规则
2. 再统一 `MediaCard / Header / Toolbar` 等基础件
3. 然后按首页、搜索、发现、详情、阅读器的顺序分阶段替换页面结构
4. 最后补齐桌面端独立布局和断点细节

这样可以先解决全站共性问题，再逐页落地具体 UI。
