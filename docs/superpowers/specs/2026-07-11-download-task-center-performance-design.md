# 下载任务中心与性能优化设计

日期：2026-07-11  
项目：`JM-Aura-Remix`

## 背景

当前下载页 `me.tasks` 已经支持任务队列、进度条、自动下载和手动下载，但仍有两个明显问题：

1. 完成态卡片仍然带有较强的“进行中”视觉，结果态不够清晰。
2. 下载页在空页面、少量历史任务、任务进行中这几个场景下占用偏高，用户反馈页面整体占用可到约 300MB，并怀疑主要来自该页面。

此外，现有任务对象只包含：

- `id`
- `type`
- `status`
- `progress`
- `result`
- `error`

它不包含“下载的是哪个本子”“如果多话下载，共几话”这类面向 UI 的信息，因此下载卡片无法准确展示任务上下文。

本次设计目标是：在保持 Remix 关键路径稳定加载和低频 SPA 刷新的前提下，重做下载页的完成态展示，并压缩该页面的渲染和刷新成本。

## 目标

- 将下载页拆为更明确的三个区域：概览、进行中、历史结果。
- 完成态卡片采用结果视图，不再沿用下载中的进度视觉。
- 下载按钮统一文案为 `下载 ZIP`，不再显示 `下载 xxxxx.zip`。
- 每个任务卡片明确显示下载对象：
  - 单本导出：显示本子标题
  - 多话导出：额外显示章节数量
  - 收藏夹导出：显示收藏夹标识和作品数量
- 下载页继续使用 SPA 低频刷新，但只让必要区域跟随刷新。
- 不引入 websocket、虚拟列表、额外的重接口或复杂缓存层。

## 非目标

- 不改变下载任务的核心执行链路。
- 不改变 ZIP 文件 2 小时保留策略。
- 不改变任务创建入口和详情页下载发起流程。
- 不在当前阶段支持大规模上百条任务的窗口化渲染。

## 设计概览

下载页拆成三个稳定区块：

1. `概览区`
2. `进行中`
3. `已完成与失败`

其中：

- 概览区是轻量统计区，可随轮询一起更新。
- 进行中区只展示 `queued / running` 任务，保留进度条和当前项文案。
- 历史区展示 `succeeded / failed / canceled` 任务，其中完成态改为结果卡片。

性能优化的核心不是减少单次请求，而是减少每次轮询后整页派生计算、整页重排序和整页卡片树重渲染。

## 数据模型变更

### 任务 metadata

在现有任务对象上增加轻量、只读、可序列化的 `metadata` 字段，用于卡片展示，不参与执行控制。

建议结构：

```ts
type TaskMetadata = {
  targetType: "album" | "favorites";
  albumId?: string;
  albumTitle?: string | null;
  chapterCount?: number | null;
  folderId?: string | null;
  folderName?: string | null;
  albumCount?: number | null;
};
```

### 字段来源

- `export_album_zip`
  - `albumId`：创建任务时已有
  - `chapterCount`：由 `chapterIds?.length` 派生；如果未传则按整本导出标记为 `null`
  - `albumTitle`：创建任务时额外查询一次漫画详情或从已有详情页上下文注入
- `export_favorites_zip`
  - `folderId`：创建任务时已有
  - `folderName`：创建任务时可根据当前收藏夹上下文传入；取不到时回退显示 `收藏夹`
  - `albumCount`：任务完成后可根据导出结果补充，或首次只为空

本次设计要求最小可落地：

- 单本任务至少能显示 `albumTitle`
- 多话任务至少能显示 `albumTitle + chapterCount`
- 收藏夹任务至少能显示 `folderName` 或 `folderId`

如果收藏夹作品数量当次难以稳定拿到，可先不展示 `albumCount`。

## 页面结构

### 概览区

展示四个统计卡片：

- 任务总数
- 进行中
- 已完成
- 失败/取消

这部分保持极轻结构，只依赖任务分组后的长度统计，不挂复杂动画。

### 进行中区

只展示 `queued / running` 任务。

每张卡片包含：

- 任务类型：`作品下载` / `收藏夹下载`
- 下载对象：如 `《作品名》`，多话时显示 `共 3 话`
- 状态：`等待中` / `进行中`
- 进度条
- 进度文案：如 `已处理 3 / 12`
- 当前项：如 `第 3 话`
- 创建时间

这一块保留当前的下载过程感，但减少无关元数据堆叠。

### 历史区

展示 `succeeded / failed / canceled`。

#### 已完成卡片

采用结果视图而不是进度视图：

- 顶部状态：`已完成`
- 任务类型和目标对象明确可见
- 不再强调大进度条
- 用轻量完成状态条或完成标识替代
- 主要信息：
  - 本子标题
  - 多话时显示 `共 N 话`
  - 文件大小
  - 完成时间
  - 提示：`保留约 2 小时，可重复下载`
- 主按钮文案统一为：`下载 ZIP`

#### 失败 / 取消卡片

- 失败：突出错误摘要
- 取消：降权展示
- 两者不再保留下载进度条主视觉

## 性能方案

### 分组优先于整页重排

当前下载页每次刷新后会对完整任务数组做排序，并渲染整页卡片列表。  
新方案先把任务分组为：

- `activeTasks`
- `historyTasks`

然后分别渲染。

这样做的目的是让历史区更稳定，避免每次轮询都和活跃区一起重排。

### 刷新边界

下载页仍然使用低频 SPA 刷新，但仅在以下条件同时满足时进行：

- 页面可见
- 存在活跃任务
- 当前不在 revalidate 中

刷新周期保持 3 秒，不再提高频率。

### 渲染边界

组件拆分为：

- `TaskQueueOverview`
- `ActiveTaskSection`
- `HistoryTaskSection`
- `TaskCard`

其中：

- 活跃区允许随轮询变化
- 历史区优先复用稳定数据
- 纯展示卡片做 memo 化
- 自动下载 effect 与卡片渲染逻辑隔离

### 降低动态样式成本

完成态卡片不再使用下载中那套强动态进度样式。  
这样可以减少：

- 动态宽度更新
- 不必要的动画
- 高频变更的内联 style

### 保持简单

由于当前任务量级确认在 10 条以内，本次不引入：

- 虚拟列表
- 窗口化渲染
- websocket
- 专门的客户端状态仓库

## 下载行为

### 自动下载

仍然保留当前行为：

- 任务从未完成状态变为 `succeeded` 时
- 自动触发一次浏览器下载
- 同一任务只触发一次

### 手动下载

完成态卡片的主按钮固定为：

- `下载 ZIP`

不再在按钮文案中拼接文件名。

文件名仍然由浏览器下载响应头决定，实际下载时仍能保留 ZIP 文件名。

## 路由与接口影响

### 前端

- `me.tasks` loader 继续直出任务列表
- 增加 `apiOrigin` 供下载 URL 构造
- 渲染层改为三区结构

### 后端

最小增量：

- 扩展任务 schema，增加 `metadata`
- 在创建任务时填入基础展示信息

其中单本下载的 `albumTitle` 建议在创建任务时就补齐，避免前端为了卡片标题再额外请求详情。

## 测试

需要补充或更新以下测试：

### 逻辑测试

- 任务分组结果稳定
- 历史区与活跃区统计正确
- 自动刷新条件不回退
- 自动下载仍只在新完成任务上触发
- 下载 URL 仍指向 API origin

### 展示测试

- 进行中卡片显示：
  - 本子标题
  - 多话数量
  - 进度条
  - 当前项
- 已完成卡片显示：
  - `已完成`
  - `下载 ZIP`
  - 文件大小
  - 完成时间
  - 2 小时保留提示
- 不再出现 `下载 xxxxx.zip`

### 回归测试

- 下载页不再出现加载失败
- 下载按钮不再 404
- 详情页创建下载任务不回退
- 自动下载不重复触发

## 风险与取舍

### metadata 补齐

本次体验优化很依赖任务 metadata。  
如果不补 metadata，前端只能展示 `album-123456` 这类弱信息，卡片质量会明显下降。

因此 metadata 被视为本次设计的一部分，而不是可选增强。

### 收藏夹统计

收藏夹导出的作品数量不纳入本次范围。  
本次先只展示：

- 收藏夹名
- 下载类型
- 完成态结果

## 验收标准

- 下载页拆成概览、进行中、历史结果三块
- 进行中任务保留进度条和当前项
- 已完成任务改为结果态卡片
- 下载按钮统一为 `下载 ZIP`
- 每个任务卡片明确展示下载对象
- 多话任务显示 `共 N 话`
- 下载页仍然只在有活跃任务时执行 SPA 低频刷新
- 历史区不再跟随每次轮询整体重排
- 页面在空页、少量历史任务、下载中三种场景下占用低于当前版本
- 自动下载、2 小时保留、手动下载能力全部保持正常
